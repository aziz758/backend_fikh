# التحليل الأكاديمي الشامل لمشروع Fi Khedmtak Backend

آخر تحديث: 2026-05-15  
نوع الوثيقة: توثيق تقني وأكاديمي لمشروع تخرج  
نطاق التحليل: Backend API، قاعدة البيانات، الخدمات الداخلية، آليات الأمان، وتدفقات العمل الرئيسية.

---

## 1. الملخص التنفيذي

مشروع `Fi Khedmtak` هو نظام Backend لمنصة خدمات ميدانية عند الطلب، يربط بين العملاء والفنيين في مجالات مثل الكهرباء، السباكة، التكييف، التنظيف، النجارة، الدهانات، الأجهزة المنزلية، والإنترنت والكاميرات.

الفكرة الأساسية أن العميل يستطيع اختيار الخدمة والمنطقة، إنشاء طلب، ثم يقوم النظام بمحاولة إسناد الطلب تلقائيا إلى فني مناسب بناء على عدة عوامل: نوع الخدمة، توفر الفني، حداثة موقعه، المسافة، ساعات العمل، التقييم، نسبة قبول الطلبات، ونسبة إكمال الطلبات.

المشروع ليس مجرد CRUD تقليدي، بل يحتوي على منطق أعمال واضح يمكن عرضه أكاديميا:

- تسجيل ودخول باستخدام OTP و JWT.
- فصل المستخدمين إلى عميل، فني، وأدمن.
- دورة حياة كاملة للطلب من الإنشاء حتى التقييم.
- خوارزمية اختيار فني تعتمد على الموقع والسمعة ومؤشرات الأداء.
- دعم المحافظات والمديريات اليمنية كجزء من خصوصية المجال المحلي.
- لوحة إدارة لمراجعة الفنيين، الخدمات المخصصة، الطلبات، المستخدمين، والتقييمات.
- إشعارات داخلية و Firebase Cloud Messaging.
- مزامنة اختيارية مع Firebase Realtime Database لتتبع حالة الطلب وموقع الفني.
- رفع صور وملفات مع تحقق أمني وفصل بين الملفات العامة والوثائق الخاصة.

## 2. مشكلة المشروع

كثير من خدمات الصيانة المنزلية والميدانية تتم بطريقة غير منظمة: اتصال مباشر، عدم وضوح سعر أو جودة الخدمة، صعوبة معرفة الفني المناسب، وعدم وجود تتبع لحالة الطلب أو تقييمات موثوقة. كما أن الفنيين أنفسهم يحتاجون إلى قناة تعرض خدماتهم وتربطهم بعملاء قريبين وملائمين.

هذا المشروع يحاول حل هذه المشكلة من خلال منصة وسيطة تنظم العلاقة بين العميل والفني والإدارة.

### المشكلة بصياغة أكاديمية

كيف يمكن بناء نظام Backend آمن وقابل للتوسع لإدارة طلبات الخدمات الميدانية، بحيث يدعم التسجيل، إدارة المستخدمين، اختيار الفنيين، تتبع الطلبات، التقييم، والإشعارات، مع مراعاة الموقع الجغرافي وسير العمل الإداري؟

## 3. أهداف المشروع

الأهداف الوظيفية:

- تمكين العميل من التسجيل، تسجيل الدخول، تحديث الملف الشخصي، اختيار خدمة، وإنشاء طلب.
- تمكين الفني من التسجيل، رفع وثائقه، تحديد مناطق خدمته وساعات عمله، استقبال الطلبات، قبولها أو رفضها، وإكمالها.
- تمكين الأدمن من مراجعة الفنيين، اعتمادهم أو رفضهم، مراجعة الخدمات المخصصة، متابعة الطلبات، وإرسال إشعارات عامة.
- توفير آلية إسناد تلقائي للطلبات إلى الفني الأنسب.
- توفير نظام تقييم ينعكس على ترتيب الفنيين.
- توفير إشعارات وتحديثات لحظية اختيارية.

الأهداف غير الوظيفية:

- رفع مستوى الأمان عبر JWT، تشفير كلمات المرور، وتجزئة OTP.
- تنظيم الكود في طبقات واضحة يسهل اختبارها وتطويرها.
- دعم قابلية التوسع بإضافة خدمات ومناطق وفنيين جدد.
- تقديم API واضح للواجهة الأمامية.
- جعل المشروع مناسبا للعرض الأكاديمي من ناحية المعمارية، النمذجة، والتحقق من القيود.

## 4. أصحاب المصلحة في النظام

### العميل

المستخدم الذي يطلب خدمة. يستطيع:

- التسجيل والدخول.
- تحديد المحافظة والمديرية والعنوان.
- استعراض الفنيين الأعلى تقييما.
- إنشاء طلب خدمة.
- متابعة حالة الطلب.
- تقييم الفني بعد إكمال الطلب.

### الفني

مقدم الخدمة. يستطيع:

- التسجيل واختيار خدماته.
- رفع صورة شخصية وصورة بطاقة/وثيقة.
- تحديد الموقع الحي.
- تحديد مناطق الخدمة.
- تحديد ساعات وأيام العمل.
- تغيير حالة التوفر.
- استقبال الطلبات وقبولها أو رفضها.
- إكمال الطلب وإضافة تقرير.

### الأدمن

المسؤول عن ضبط جودة المنصة. يستطيع:

- مراجعة الفنيين ووثائقهم.
- قبول أو رفض الفنيين.
- مراجعة الخدمات التي يكتبها الفني كخدمة مخصصة.
- متابعة الإحصائيات والطلبات والتقييمات.
- إدارة المستخدمين بتعطيل الحسابات.
- إرسال إشعارات عامة أو موجهة.

## 5. التقنيات المستخدمة وسبب استخدامها

| التقنية | مكان استخدامها | سبب الاستخدام |
|---|---|---|
| Python | لغة المشروع الأساسية | لغة مناسبة لبناء APIs بسرعة، ولها مكتبات قوية للويب وقواعد البيانات والأمان. |
| FastAPI `0.115.6` | بناء REST API | إطار سريع وحديث، يدعم OpenAPI/Swagger تلقائيا، ويعتمد على type hints و Pydantic للتحقق من البيانات. |
| Uvicorn `0.32.1` | تشغيل التطبيق كخادم ASGI | مناسب لتشغيل FastAPI في التطوير والإنتاج الخفيف. |
| SQLAlchemy `2.0.36` | ORM وطبقة التعامل مع قاعدة البيانات | يعزل منطق قواعد البيانات عن SQL الخام، ويمثل الجداول ككلاسات Python. |
| MySQL عبر PyMySQL `1.1.1` | قاعدة البيانات | قاعدة علائقية مناسبة للعلاقات بين العملاء، الفنيين، الطلبات، الخدمات، المناطق، والتقييمات. |
| Pydantic | Schemas والتحقق من المدخلات | يضمن أن الطلبات والاستجابات لها بنية واضحة، ويقلل أخطاء البيانات القادمة من الواجهة. |
| JWT عبر `python-jose` | المصادقة | يسمح بإصدار access token للمستخدم بعد الدخول، واستخدامه في endpoints المحمية. |
| Passlib + bcrypt | تشفير كلمات المرور | تخزين كلمة المرور بشكل hash بدلا من نص صريح. |
| HMAC/SHA-256 | تجزئة OTP | تخزين كود التحقق بشكل hash مرتبط بالهاتف ونوع المستخدم بدلا من حفظ الكود مباشرة. |
| python-multipart | رفع الملفات | مطلوب من FastAPI لمعالجة `multipart/form-data`. |
| httpx | إرسال OTP عبر مزود SMS | عميل HTTP غير متزامن مناسب للتكامل مع مزودي الرسائل. |
| python-dotenv | قراءة `.env` | يسهل فصل الإعدادات الحساسة عن الكود. |
| Firebase Admin `7.1.0` | FCM وRealtime Database | إرسال push notifications ومزامنة حالة الطلب/الموقع في الزمن الحقيقي. |
| tzdata + zoneinfo | أوقات عمل الفنيين | دعم المناطق الزمنية، خصوصا على Windows أو البيئات التي لا تحتوي قاعدة timezone كاملة. |

ملاحظة تقنية: مكتبة `pydantic-settings` موجودة في `requirements.txt`، لكن ملف الإعداد الحالي `app/config.py` يستخدم كلاس `Settings` مخصص وقراءة مباشرة من البيئة. يمكن مستقبلا تحويل الإعدادات إلى `BaseSettings` إذا أراد الفريق نمطا معياريا أكثر.

## 6. المعمارية العامة

المشروع يستخدم معمارية طبقية بسيطة وواضحة:

```text
Client Apps
    |
    | HTTP / JSON / Multipart
    v
FastAPI Routers - app/api
    |
    | Depends, validation, permissions
    v
Services - app/services
    |
    | business logic
    v
Models - app/models
    |
    | SQLAlchemy ORM
    v
MySQL Database

Optional:
FastAPI -> Firebase FCM / Realtime Database
```

### فكرة الفصل بين الطبقات

- `api`: يستقبل الطلبات HTTP ويتحقق من الصلاحيات ويرجع الاستجابات.
- `schemas`: يحدد شكل البيانات الداخلة والخارجة باستخدام Pydantic.
- `models`: يحدد جداول قاعدة البيانات والعلاقات بينها باستخدام SQLAlchemy.
- `services`: يحتوي منطق الأعمال القابل لإعادة الاستخدام، مثل المصادقة، الإسناد، التحقق من الموقع، الإشعارات، ورفع الملفات.
- ملفات migrations و seeds: تضبط قاعدة البيانات وتملأها ببيانات أولية.

هذا الفصل مهم أكاديميا لأنه يوضح مبدأ Separation of Concerns، حيث لا يتم خلط منطق HTTP مع منطق قاعدة البيانات أو خوارزميات الاختيار.

## 8. نموذج البيانات

قاعدة البيانات علائقية، وهذا مناسب لأن المشروع يحتوي علاقات كثيرة: عميل لديه طلبات، فني يقدم عدة خدمات، طلب قد يحتوي عدة خدمات، فني لديه مناطق خدمة، تقييم مرتبط بطلب، وهكذا.

### الجداول الرئيسية

| الجدول | الغرض |
|---|---|
| `customers` | بيانات العملاء، الهاتف، كلمة المرور المشفرة، الحالة، FCM token، الصورة، الموقع، المحافظة، المديرية. |
| `technicians` | بيانات الفنيين، الحالة، التوفر، التقييم، نسب الأداء، الموقع الحي، منطقة العمل، الوثائق، إعدادات العمل. |
| `services` | الخدمات الرسمية التي يختارها العميل أو الفني. |
| `service_categories` | تصنيف الخدمات إلى مجموعات مثل تنظيف، كهرباء، سباكة. |
| `technician_services` | علاقة many-to-many بين الفنيين والخدمات الرسمية. |
| `technician_service_areas` | مناطق خدمة الفني، إما محافظة كاملة أو مديرية محددة. |
| `technician_service_requests` | الخدمات المخصصة التي يطلب الفني إضافتها قبل اعتمادها من الأدمن. |
| `requests` | طلبات العملاء وحالتها والفني المسند والموقع والتقييم والتقرير. |
| `request_services` | الخدمات المرتبطة بكل طلب. |
| `request_assignments` | سجل محاولات إسناد الطلب للفنيين، مع حالات pending/accepted/rejected/timeout/cancelled. |
| `ratings` | تقييمات العملاء للفنيين، مرتبطة غالبا بطلب محدد. |
| `reviews` | سجل إضافي مرتبط بالطلب والفني، يبدو أنه يدعم منظور مراجعة/قبول من الفني. |
| `otp_verifications` | أكواد OTP المجزأة ومواعيد انتهائها. |
| `notifications` | إشعارات داخلية مخزنة لكل مستخدم. |
| `governorates` | المحافظات. |
| `districts` | المديريات المرتبطة بمحافظة. |

### علاقات مهمة

- `Customer` لديه عدة `Request` وعدة `Rating`.
- `Technician` لديه عدة خدمات عبر `TechnicianService`.
- `Technician` لديه عدة مناطق خدمة عبر `TechnicianServiceArea`.
- `Request` يتبع `Customer` وقد يسند إلى `Technician`.
- `Request` يحتوي خدمات عبر `RequestService`.
- `Rating` يربط العميل والفني والطلب.
- `District` يتبع `Governorate`.

### قيمة النموذج أكاديميا

النموذج يوضح مفاهيم:

- One-to-many مثل: عميل -> طلبات.
- Many-to-many عبر جدول وسيط مثل: فني -> خدمات.
- Optional relationships مثل: الطلب قد لا يكون مسندا لفني بعد.
- Historical tracking مثل: `request_assignments` يحفظ سجل الرفض والمهلة وليس فقط الحالة الحالية.
- Context preservation مثل: حفظ المحافظة والمديرية داخل الطلب والتقييم حتى لو تغير ملف المستخدم لاحقا.

## 9. المستخدمون والصلاحيات

النظام يتعامل مع ثلاثة أدوار:

```text
customer
technician
admin
```

### كيف يتم تحديد الأدمن؟

الأدمن يتم تمثيله كعميل في جدول `customers` مع عمود `is_admin = true`. عند قراءة التوكن، إذا كان `user_type = customer` ويملك المستخدم `is_admin`، تقوم `get_current_user` بإرجاع النوع كـ `admin`.

هذا حل عملي في مشروع تخرج لأنه يقلل الحاجة إلى جدول مستخدمين عام جديد، لكنه في الإنتاج يمكن تطويره إلى نموذج RBAC مستقل.

### حماية endpoints

- `require_customer`: يسمح فقط للعميل.
- `require_technician`: يسمح فقط للفني.
- `require_admin`: يسمح فقط للأدمن.
- `get_current_user_id`: يتحقق من JWT ومن وجود المستخدم ومن أن الحساب ليس `inactive`.

## 10. تدفق المصادقة والتسجيل

### 10.1 إرسال OTP

العميل أو الفني يرسل رقم الهاتف ونوع المستخدم:

```text
POST /api/auth/send-otp
```

النظام:

1. يولد كود OTP باستخدام `secrets`.
2. يحفظ hash للكود في قاعدة البيانات.
3. يرسل الكود عبر SMS إذا كانت إعدادات مزود الرسائل موجودة.
4. في وضع التطوير يطبع الكود في الـ console إذا لم توجد إعدادات SMS.

### 10.2 التحقق من OTP

```text
POST /api/auth/verify-otp
```

إذا الرقم موجود مسبقا:

- يرجع access token.

إذا الرقم غير مسجل:

- يرجع `registration_token` قصير العمر.

### 10.3 التسجيل

التسجيل لا يتم مباشرة برقم الهاتف فقط؛ يجب إرسال `registration_token`. هذا يمنع إنشاء حساب بدون تحقق فعلي من رقم الهاتف.

```text
POST /api/auth/register/customer
POST /api/auth/register/technician
```

### 10.4 تسجيل الدخول

```text
POST /api/auth/login
```

النظام يتحقق من:

- وجود المستخدم.
- صحة كلمة المرور باستخدام bcrypt.
- أن الحساب ليس `inactive`.
- ثم يصدر JWT.

### نقطة قوة أمنية

OTP لا يخزن كنص صريح، بل كـ HMAC-SHA256 باستخدام `SECRET_KEY` مع الهاتف ونوع المستخدم والكود. كما أن OTP يحذف بعد نجاح التحقق، وهذا يقلل خطر إعادة الاستخدام.

## 11. دورة حياة الطلب

حالات الطلب الأساسية:

```text
pending -> assigned -> accepted -> completed
```

ويمكن الإلغاء في مراحل معينة:

```text
pending -> cancelled
assigned -> cancelled
accepted -> cancelled
```

هذه الانتقالات مضبوطة في `app/services/request_state_machine.py`، وهذا يمنع القفز العشوائي بين الحالات، مثل تحويل طلب مكتمل إلى قيد التنفيذ.

### إنشاء طلب

```text
POST /api/requests/
```

العميل يرسل:

- الخدمات المطلوبة `service_ids`.
- الملاحظات.
- الصورة إن وجدت.
- الموقع `lat/lng`.
- العنوان.
- المحافظة والمديرية.

إذا لم يرسل العميل المحافظة والمديرية، يحاول النظام استخدام المنطقة المحفوظة في ملف العميل.

### إسناد الطلب

بعد إنشاء الطلب يحاول النظام اختيار فني مناسب للخدمة الأولى في الطلب. إذا وجد فني:

- ينشئ سجل في `request_assignments`.
- يحول حالة الطلب إلى `assigned`.
- يرسل إشعارا للفني.
- يبدأ مهلة 5 دقائق لقبول الطلب.

إذا لم يجد فني:

- يبقى الطلب في حالة مناسبة حسب المنطق الحالي، وغالبا لا يتم إسناده مباشرة.

### قبول الطلب

```text
POST /api/requests/{request_id}/accept
```

شروط قبول الفني:

- الطلب مسند لهذا الفني.
- لدى الفني موقع حي حديث.
- لا يملك الفني طلبا نشطا آخر.
- يوجد سجل assignment بحالة `pending`.

بعد القبول:

- تتحول حالة الطلب إلى `accepted`.
- يتحول الفني إلى `busy`.
- يتم إعلام العميل.
- يتم إلغاء عروض أخرى معلقة على نفس الفني وإعادة إسنادها عند الحاجة.

### رفض الطلب

```text
POST /api/requests/{request_id}/reject
```

يتطلب سبب رفض. عند الرفض:

- يحفظ السبب في `request_assignments`.
- يتم تحديث نسبة قبول الفني.
- يحاول النظام العثور على فني بديل.
- إذا لم يجد فني بديل، يتم إلغاء الطلب وإعلام العميل.

### إكمال الطلب

```text
POST /api/requests/{request_id}/complete
```

الفني يرسل تقريرا. بعد الإكمال:

- تتحول الحالة إلى `completed`.
- تحفظ قيمة `technician_report`.
- تحدث نسبة الإكمال للفني.
- يعود الفني إلى `available` إذا كان موقعه حديثا، وإلا إلى `offline`.
- يتم إعلام العميل للتقييم.

### تقييم الطلب

```text
POST /api/requests/{request_id}/rate
```

التقييم متاح فقط للطلبات المكتملة. النظام:

- يحفظ التقييم في الطلب.
- ينشئ سجل `Rating`.
- يحدث متوسط تقييم الفني وعدد التقييمات.
- يرسل إشعارا للفني.

## 12. خوارزمية اختيار الفني

ملف `app/services/assignment_service.py` يحتوي منطق اختيار الفني الأفضل.

### شروط الدخول في قائمة المرشحين

الفني يجب أن:

- يقدم الخدمة المطلوبة.
- حسابه `approved`.
- حالته `available` أو غير محددة.
- لديه `lat/lng`.
- لديه `location_updated_at` حديث حسب TTL.
- لا يملك طلبا نشطا بحالة `accepted`.
- داخل ساعات العمل إن كانت محددة.
- داخل نطاق المسافة المسموحة.

### حساب المسافة

المشروع يستخدم معادلة Haversine لحساب المسافة بين إحداثيات العميل والفني بالكيلومتر. هذه المعادلة مناسبة لأنها تحسب المسافة على سطح الأرض بين نقطتين جغرافيتين.

### حساب الأولوية

ملف `app/services/technician_priority_service.py` يحسب score للفني بناء على:

- المسافة.
- متوسط التقييم.
- نسبة قبول الطلبات.
- نسبة إكمال الطلبات.

الأوزان الافتراضية من الإعدادات:

```text
TECHNICIAN_PRIORITY_DISTANCE_WEIGHT=0.5
TECHNICIAN_PRIORITY_RATING_WEIGHT=0.25
TECHNICIAN_PRIORITY_ACCEPTANCE_WEIGHT=0.15
TECHNICIAN_PRIORITY_COMPLETION_WEIGHT=0.1
```

المعادلة العامة:

```text
priority = weighted_average(distance_score, rating_score, acceptance_score, completion_score)
```

إذا لم تكن المسافة متاحة، يتم تجاهل وزن المسافة وإعادة توزيع التأثير على بقية المعايير.

### الأهمية الأكاديمية للخوارزمية

الخوارزمية لا تختار أول فني فقط، بل تستخدم ترتيب متعدد المعايير. هذا يعطي المشروع قيمة أكبر في المناقشة؛ لأنه يحول المشكلة من CRUD إلى Decision Support داخل النظام.

## 13. عرض الفنيين الأعلى تقييما

يوجد فرق مهم بين:

```text
GET /api/technicians/top
GET /api/technicians/nearby
```

### `/api/technicians/top`

الغرض منه الاستعراض. يستخدم عندما يريد العميل تصفح أفضل الفنيين حسب الخدمة والمنطقة. لا يشترط أن يكون الفني متاحا الآن أو أن يكون موقعه حديثا.

يرتب الفنيين بناء على:

- مطابقة المنطقة.
- متوسط التقييم.
- عدد التقييمات.
- التعليقات الإيجابية.
- نسبة الإكمال.
- نسبة القبول.

يستخدم أيضا فكرة Bayesian weighted rating حتى لا يتفوق فني لديه تقييم واحد 5 نجوم دائما على فني لديه عدد كبير من التقييمات الجيدة.

### `/api/technicians/nearby`

الغرض منه الطلب الفوري. يعرض فقط الفنيين المتاحين حاليا، بموقع حديث، داخل المسافة، وداخل ساعات العمل.

هذا الفصل بين الاستعراض والإسناد الفوري نقطة تصميم جيدة لأنها تمنع خلط تجربة "اختيار فني مشهور" مع تجربة "أحتاج فني متاح الآن".

## 14. المواقع والمناطق

المشروع يحتوي على:

- `governorates`: محافظات.
- `districts`: مديريات.

ملف `seed_locations.py` يضيف بيانات أولية لمحافظات ومديريات يمنية. هذا يجعل المشروع مرتبطا بسياق محلي واضح.

### قواعد التحقق

ملف `location_validation_service.py` يضمن:

- لا يمكن إرسال `district_id` بدون `governorate_id`.

### استخدام المنطقة في المشروع

- العميل لديه منطقة محفوظة.
- الفني لديه منطقة أساسية.
- الفني يمكنه تحديد عدة مناطق خدمة.
- الطلب يحفظ سياق المنطقة عند الإنشاء.
- التقييم يمكن ربطه بالطلب وبالتالي بالمنطقة.
- ترتيب الفنيين يمكن أن يستخدم سمعتهم داخل منطقة محددة.

## 15. ملف الفني واعتماده

حالات حساب الفني:

```text
pending_documents
pending_approval
approved
rejected
inactive
```

### دورة اعتماد الفني

1. الفني يسجل.
2. حالته تصبح `pending_documents`.
3. يرفع الصورة الشخصية وصورة الهوية/البطاقة.
4. حالته تصبح `pending_approval`.
5. الأدمن يراجع الوثائق والخدمات.
6. الأدمن يوافق أو يرفض.

### حماية وثائق الفني

الصورة الشخصية تحفظ كملف عام لأنها تظهر للعملاء. أما صورة الهوية فتحفظ في:

```text
private_uploads/technician_documents
```

ولا تفتح عبر `/uploads` العام. الوصول لها يتم فقط عبر endpoint محمي:

```text
GET /api/technician/profile/documents/id-card
GET /api/admin/technicians/{technician_id}/documents/id-card
```

وهذه نقطة أمنية مهمة يمكن ذكرها في العرض؛ لأن النظام يفرق بين الصور العامة والوثائق الحساسة.

الخدمات الرسمية موجودة في جدول `services` ومصنفة عبر `service_categories`. ملف `seed_services.py` يضيف كتالوج خدمات يشمل:

- نجارة.
- دهانات.

الأدمن يستطيع:

- إنشاء اسم رسمي جديد للخدمة.

ولا يمكن اعتماد الفني إذا كان لديه خدمات مخصصة معلقة. هذا يحافظ على جودة كتالوج الخدمات ويمنع ظهور أسماء غير منظمة للعملاء.

## 23. الجوانب الأمنية

### نقاط قوة موجودة

- كلمات المرور تخزن باستخدام bcrypt.
- JWT يستخدم للوصول للـ endpoints المحمية.
- OTP يخزن مجزأ وليس كنص صريح.
- OTP يحذف بعد نجاح التحقق.
- registration token يمنع التسجيل قبل تحقق الهاتف.
- الحسابات inactive تمنع من الدخول واستخدام endpoints المحمية.
- رفع الصور مقيد بالامتداد، content type، والحجم.
- وثائق الفنيين محفوظة في مسار خاص وليست عامة.
- `RequestCreate` وبعض schemas تمنع الحقول الزائدة باستخدام `extra="forbid"`.
- صلاحيات customer/technician/admin مفصولة.

### نقاط تحتاج تحسين قبل إنتاج فعلي

- `allow_origins=["*"]` مناسب للتطوير، لكن في الإنتاج يجب تحديد دومينات الواجهة فقط.
- إضافة rate limiting على OTP و login لتقليل محاولات التخمين.
- نقل الأسرار مثل `.env` وملفات Firebase credentials خارج أي مستودع عام.
- إضافة audit log لقرارات الأدمن.
- استخدام storage خارجي آمن للملفات مثل S3 أو Firebase Storage مع signed URLs.
- توسيع RBAC بدلا من تمثيل الأدمن كعميل بحقل إضافي فقط.

- بعض العمليات الخلفية مثل timeout تعمل بخيوط داخل التطبيق؛ في الإنتاج الأفضل استخدام worker/queue مثل Celery/RQ.
- migrations يدوية؛ الأفضل اعتماد Alembic.
- يمكن توحيد `created_at` والتواريخ timezone-aware بشكل أقوى.
- يمكن إضافة OpenAPI tags ووصف أوسع لكل endpoint.
- يمكن إضافة logging منظم بدلا من `print` في بعض المسارات التطويرية.

## 27. نقاط أكاديمية يمكن التركيز عليها

### 27.1 Engineering Design

المشروع يطبق مبدأ فصل المسؤوليات، ويقسم المنطق إلى طبقات. هذا يسهل الصيانة والاختبار ويجعل كل جزء واضحا:

- Router للتعامل مع HTTP.
- Schema للتحقق من البيانات.
- Service لمنطق الأعمال.
- Model لقاعدة البيانات.

### 27.2 Data Modeling

قاعدة البيانات مصممة حول علاقات واقعية:

- فني يقدم عدة خدمات.
- طلب يحتوي عدة خدمات.
- فني يخدم عدة مناطق.
- تقييم مرتبط بطلب وفني وعميل.

### 27.3 Algorithmic Thinking

اختيار الفني يستخدم weighted scoring وليس اختيارا عشوائيا. هذا يوضح قدرة المشروع على اتخاذ قرار مبني على بيانات.

### 27.4 Security Awareness

المشروع لا يخزن كلمات المرور أو OTP بشكل مكشوف، ويفصل الوثائق الحساسة عن الصور العامة.

### 27.5 Local Context

وجود محافظات ومديريات يمنية وخدمات منزلية محلية يجعل المشروع أكثر واقعية وارتباطا ببيئة المستخدمين.

## 28. حدود المشروع الحالية

- لا توجد اختبارات آلية واضحة في المستودع الحالي.
- لا توجد Alembic migrations.
- CORS مفتوح لكل المصادر في التطوير.
- لا توجد rate limits لطلبات OTP.
- لا يوجد نظام دفع أو تسعير.
- لا يوجد chat بين العميل والفني.
- لا توجد سياسة صلاحيات إدارية متعددة المستويات.
- ملفات الرفع تحفظ محليا، وهذا مناسب للتطوير لكنه يحتاج تخزين خارجي في الإنتاج.

## 30. الخلاصة

مشروع `Fi Khedmtak Backend` يقدم Backend متكامل لمنصة خدمات ميدانية، ويغطي دورة العمل الأساسية من التسجيل إلى الطلب والإسناد والتتبع والتقييم والإدارة. أهم ما يميز المشروع أكاديميا أنه يحتوي على:

- نموذج بيانات غني.
- صلاحيات متعددة.
- خوارزمية اختيار فني.
- توثيق واجهة.
- اعتبارات أمنية حقيقية.
- ربط اختياري مع Firebase للتتبع والإشعارات.
- سياق محلي واضح عبر المحافظات والمديريات وكتالوج الخدمات.

لذلك يمكن تقديمه كمشروع تخرج قوي إذا تم التركيز أثناء العرض على المشكلة، التصميم، الخوارزمية، الأمان، ودورة العمل الكاملة بدلا من عرض endpoints فقط.
